# PRD - Daycare Waitlist Fee Scout

## Problem
- First-time parents track daycare waitlist fees, tour notes, openings, and backup coverage before a return-to-work date collapses.

## Target user
- First-time parents and dual-income families trying to secure infant or toddler daycare before parental leave ends.

## Key UX
- Parent enters target start date, centers, waitlist fees, tour notes, age-room openings, commute, and backup caregivers; the app ranks which centers need calls, deposits, or fallback plans.

## Required UI sections
- Return-to-work countdown header
- Center pipeline with waitlist position, fee paid, age room, and tour status
- Application-fee ledger and refundability flags
- Call-back cadence and script builder
- Backup care coverage map for grandparents, nanny share, and part-time care
- Commute and pickup stress comparison
- Decision board for hold, chase, deposit, or abandon

## Assigned design profile
- calm-consumer

- 외로움 / 자산 방어 - working-parent anxiety, childcare scarcity, and career continuity.

## Stitch prompt
Build a production-grade web app prototype called "Daycare Waitlist Fee Scout" for first-time parents tracking daycare waitlist fees, tour notes, openings, and backup coverage before a return-to-work date collapses. The first screen must be a working parent planning console with a return-to-work countdown, center pipeline, application-fee ledger, callback script builder, backup care coverage map, commute comparison, and decision board. Use realistic sample data: 74 days until work return, six centers, two $125 waitlist fees, one year-plus waitlist, infant room opening in August, grandparent backup only Tuesdays, and two centers needing follow-up calls. Design direction: use the calm-consumer profile with low-stress family planning cards, gentle progress states, friendly but compact forms, and one soft teal accent for the next call. Do not make a marketing landing page; the first screen must be the working app.

## Constraints
- Phase A only: do not implement a custom demo.
- First screen in Stitch must be the working app, not a marketing landing page.
- Use external sources as problem evidence only, not market-size proof.

## Non-goals
- No external API integration in the prototype.
- No legal, medical, financial, or regulatory advice claims beyond workflow support.

## Success metrics
- User can understand the pain in under 10 seconds.
- User can identify the next action from the first screen.
- The prototype includes every required UI section from this PRD.
