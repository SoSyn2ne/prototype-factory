# Assumptions (KNOWN / ASSUMPTION / UNKNOWN)

## KNOWN
- Wedding seating is a high-stakes social system: small placement choices can cause outsized feelings.
- Most “hard” seating requirements can be expressed as pairwise relationships (A cannot sit near B; C needs to sit near D).
- Couples already track guests in a spreadsheet or planning tool, but relationship constraints live in chats and memory.
- The most painful changes happen late: one new constraint forces moving several people, which creates new conflicts.

## ASSUMPTION
- A friction “hotspot” view (sum of weighted constraints touching a guest) helps users prioritize where to spend decision-making time.
- Users can meaningfully pick a 1–3 importance weight without overthinking:
  - 1 = preference, 2 = important, 3 = non‑negotiable.
- Users will input the *top* constraints (the ones that cause drama) even if they do not input every preference.
- A simple “bride side / groom side” tag is enough context to orient many couples during planning (without building full family trees).
- An adjacency matrix (small, scrollable) is an acceptable visualization for early-stage planning.

## UNKNOWN
- Typical constraint volume: for 80–120 guests, is it ~10, ~30, or ~100 pairwise constraints?
- Which constraint type dominates in practice: “must-separate” (conflict avoidance) or “must-sit-near” (comfort / bonding)?
- Do users prefer adding constraints by searching names, by clicking in a matrix, or by importing from a sheet?
- How often do constraints need directional nuance (e.g., “A can tolerate B but B can’t tolerate A”)?
- Does “side” create bias (e.g., users assume sides must be separated) and should the UI discourage that?
