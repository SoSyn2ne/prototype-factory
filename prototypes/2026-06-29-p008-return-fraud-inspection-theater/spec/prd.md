# PRD - Return Fraud Inspection Theater

## Problem
- Small ecommerce teams stage suspicious returns, box photos, customer history, and refund rules into a fast approve-deny performance.

## Target user
- Small ecommerce sellers, boutique retail ops teams, and returns coordinators dealing with wardrobing, empty boxes, swapped items, and serial refund abuse.

## Key UX
- Operator opens a suspicious return case, reviews unboxing evidence and customer history, runs policy tests, and chooses approve, partial refund, deny, or manual escalation.

## Required UI sections
- Suspicious return stage with order value, item, claim type, and refund deadline
- Unboxing photo strip and weight-scan timeline
- Customer history and network-risk clues
- Policy test cards for honest-customer protection vs abuse prevention
- Approve, partial, deny, or escalate decision rail
- Customer reply composer that stays firm without sounding accusatory
- Weekly fraud pattern wall with repeat items, ZIPs, and claim reasons

## Assigned design profile
- playful-experimental

- 자산 방어 / 역전 - merchant loss prevention with a shareable case-stage metaphor.

## Stitch prompt
Build a production-grade web app prototype called "Return Fraud Inspection Theater" for small ecommerce teams staging suspicious returns, box photos, customer history, and refund rules into a fast approve-deny performance. The first screen must be a working returns case surface with a suspicious return stage, unboxing photo strip, weight-scan timeline, customer history clues, policy test cards, decision rail, customer reply composer, and weekly fraud pattern wall. Use realistic sample data: $289 dress returned after event weekend, package weight mismatch, missing tag photo, repeat buyer with six returns, honest-customer risk note, empty-box claim, and one organized-network warning. Design direction: use the playful-experimental profile with a memorable stage/backstage composition, bold but readable contrast, one magenta action accent, and recognizable operations controls beneath the concept. Do not make a marketing landing page; the first screen must be the working app.

## Constraints
- Phase A only: do not implement a custom demo.
- First screen in Stitch must be the working app, not a marketing landing page.
- Use external sources as problem evidence only, not market-size proof.

## Non-goals
- No external API integration in the prototype.
- No legal, medical, financial, or regulatory advice claims beyond workflow support.

## Success metrics
- User can understand the pain in under 10 seconds.
- User can identify the next action from the first screen.
- The prototype includes every required UI section from this PRD.
