# Falsification checklist (7)

1. If users don’t know their average watts and won’t look it up, the input model fails.
2. If “runtime fixed” makes the cap what-if misleading (runtime changes dominate), the calculator needs a throughput model.
3. If electricity price is too variable/unknown for users, estimates won’t feel trustworthy.
4. If users primarily care about *time-to-result* and not cost, this won’t be used.
5. If carbon factor feels like noise/virtue signaling, the CO₂ output should be optional.
6. If existing tools (Home Assistant energy, smart plugs, datacenter billing) already solve it, this is redundant.
7. If the UI isn’t copy-friendly for reports, it won’t fit an ops workflow.
